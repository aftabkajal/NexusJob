# Reconciliation — PRD vs. UX Spines

## Covered cleanly

- **Vision / non-differentiation framing (§1):** Doesn't need a literal UX manifestation and doesn't get one — no feature creep toward differentiation is visible in either spine. The "consumer-grade stakes" choice (full AA floor, recalculated color contrast, editorial polish) is a deliberate tension against the PRD's "practice vehicle, not a market product" framing, but it's already logged in `.memlog.md` line 7 ("Stakes: consumer-grade... despite PRD framing this as a practice/learning project") — noted here, not re-litigated.
- **UJ-1 / UJ-2 (§2.2):** Realized near-verbatim as EXPERIENCE.md Key Flows 1 and 2, including both flows' failure paths (duplicate-email registration; apply-submit network failure).
- **FR-1/FR-2 (auth):** Error copy in EXPERIENCE.md State Patterns matches PRD consequence text almost word-for-word ("This email is already registered as a Company"; sign-in error explicitly cites "per PRD FR-1/FR-2" and preserves the "don't reveal which field was wrong" rule).
- **FR-3 out-of-scope (no edit/deactivate/delete):** Actively guarded, not just silently absent — EXPERIENCE.md's "Posting not found" state explicitly says "since v1 has no edit/deactivate lifecycle but a posting could still be mistyped or the id invalid," directly citing the PRD constraint while handling the adjacent edge case.
- **FR-4/FR-5 (open search, no facets):** Submit-to-search, substring match, no location/salary filters, no account required for browse/search/view — all explicit in both spines. This assumption originates in the PRD's own Assumptions Index (§10), so the spines are carrying forward a PRD-logged call, not making a new one.
- **FR-6 (apply, one-per-pair):** `apply-button` state table explicitly ties the disabled "Applied" state to "the PRD's one-application-per-pair rule" — a rare case of the spine citing its source inline.
- **FR-7 (no scoring/ranking/filtering/status):** This is the item the task flagged as a risk, and it's well handled — both spines state the constraint as a deliberate design absence, not just an omission: DESIGN.md's `applicant-row` entry ("No action controls on the row — the surface has no scoring, filtering, or status workflow") and EXPERIENCE.md's Component Patterns row ("Read-only — no click action, no per-row controls (no scoring/status per PRD scope)").
- **FR-7 ownership scoping:** "A Company can only view Applicants for Job Postings it created" is covered by a dedicated State Pattern ("Permission denied... treated the same as 'not found', never a 'blocked' screen that confirms the posting exists") — stronger than the PRD's bare requirement.
- **Non-Goals — not an ATS, not mobile, no multi-tenant company accounts:** No interview-stage/offer/rejection workflow, no responsive/mobile treatment (explicitly stated as a deliberate NFR-driven choice in both spines), and no team/role concept within a Company account anywhere in the IA.
- **MVP out-of-scope checklist (§6.2):** Resume upload, status tracking beyond "applied," messaging/notifications, search filters beyond keyword, admin/moderation, payments, SSO/verification — none of these leak into either spine. The "My Applications" surface (not in the PRD's explicit feature list, but implied by MVP scope) is called out in memlog as a new surface with "no status tracking" stated explicitly.
- **SM-1 (core loop end-to-end):** Fully dramatized across Key Flows 1 and 2 (post → search → view → apply → view applicants).
- **Glossary terms:** No synonym drift — no "employer" for Company, no "candidate" for Applicant/Job Seeker, no "listing" substituting for "Job Posting" as an entity (it's only used generically for "the list of postings" on screen). See Terminology section below for the one stylistic note.

## Gaps / dropped ideas

- **No account-creation field for "name" — Company or Job Seeker — despite both being displayed.** FR-5 requires posting detail to display "the name of the Company that posted it," and FR-7's consequence gives "for example, name/email" for Applicant identifying info. Neither spine's Sign up/Log in surface, `auth-role-toggle` component, or Flow steps ever collect a name at registration (Flow 1 step 2 and Flow 2 step 5 both say only "enters an email and password and submits"). Yet DESIGN.md's `job-card` shows "company name" as a meta field, and both `applicant-row` (DESIGN.md, with a dedicated `name-typography` token) and EXPERIENCE.md's Flow 1 climax ("the Applicants list shows real names, emails...") assert a name is always present and displayed. This is a real, unaddressed data-collection gap the spines inherited from the PRD (whose FR-1/FR-2 don't mention a name field) without either resolving it or flagging it as still open — see the corresponding item below.
- No other clear drops found. FR-3's "non-empty title/description" validation isn't spelled out field-by-field in Interaction Primitives, but it's reasonably covered by the generic "validate on blur and on submit" rule — minor, not worth a strong flag.

## Assumptions made without a paper trail

- **Applicant/Company "name" field (see Gap above) — no trace at all.** This is the single most important item: PRD Open Question #2 ("What minimum applicant fields ... is a name required at sign-up?") is explicitly listed as unresolved in the PRD, and the spines resolve it by *assuming yes* (a name exists and displays) but never say so — not in the spine text, not in `.memlog.md`. Unlike the "no edit/deactivate lifecycle" case (which cites the open question inline) or the consumer-grade-stakes case (logged in memlog), this one has zero paper trail. An implementer following the spines alone would not know where "name" comes from.
- **PRD Open Question #1 (editable/deactivatable postings):** Already logged — EXPERIENCE.md's "Posting not found" state cites "v1 has no edit/deactivate lifecycle" directly. Fine as-is.
- **PRD Open Question #3 (search requires account?):** Not a UX-originated assumption — FR-4 itself already carries this as a PRD-logged assumption (§10 Assumptions Index), and the spines simply implement it faithfully. No new, untracked call being made here.
- **PRD Open Question #4 (email uniqueness scoped per role or global):** The spines' error copy ("already registered as a Company" / "...as a Job Seeker" — role-specific phrasing) implicitly leans toward per-role uniqueness (the same email could register as both a Company and a Job Seeker), but this phrasing is inherited verbatim from FR-1/FR-2's own consequence text, not a UX decision. The underlying data-model ambiguity the PRD flagged is still genuinely open and unaddressed by either spine or memlog — worth carrying forward into architecture rather than treating as resolved.

## Terminology consistency

Substantively consistent — no glossary term is swapped for a synonym across either document (no "employer," "candidate," or "listing" used in place of Company, Applicant/Job Seeker, or Job Posting). There is a minor, low-stakes stylistic inconsistency in capitalization: EXPERIENCE.md's IA table capitalizes "Job Posting(s)" when referring to the entity (matching the glossary) but lowercases it elsewhere as a common noun ("his posting," "postings," "job posting detail" as a surface name); DESIGN.md does the same. This reads as normal prose-vs-proper-noun variation rather than a meaning conflict, but flagging it since the task asked about verbatim consistency.
