Executive summary

The 2025–26 consensus is not "Clean Architecture vs. Vertical Slice" or "modular monolith vs. microservices" as binary choices — it's a hybrid, and the requester's stack maps onto a well-trodden (if not perfectly documented) path. Structure the .NET backend as a modular monolith, one module per Domain-Driven Design (DDD) bounded context with a compiler-enforced Contracts-only public surface [1][22][28]; inside each module, default to Vertical Slice Architecture for feature velocity and reserve full layered Clean Architecture for modules with genuinely complex, long-lived domain logic [20][19]. On the frontend, Feature-Sliced Design is the closest React analogue, organizing slices by business capability the same way bounded contexts organize the backend [5][25] — but this specific backend↔frontend mapping is a design hypothesis this research validates in principle, not a pattern anyone has published a named production case study for.

The single biggest live risk isn't architectural, it's a licensing shock: MediatR, AutoMapper, and MassTransit — the default tooling trio for CQRS-style .NET DDD — went commercial in 2025 under Jimmy Bogard's Lucky Penny Software [34][64][72]. Any recommendation resting on "just use MediatR" now carries a cost decision that didn't exist 18 months ago. A second, quieter risk: the widely-cited "Gartner: 60% of teams regret microservices" statistic does not trace to any real Gartner document — it should never be repeated [63].

Biggest caveat: every source found treats DDD-tactics, Clean-Architecture-.NET, and modular-React as three separate literatures. No named team's 6–12 month retrospective covers the combined stack the requester is about to build — the recommendations below are well-supported component by component, not validated as a combined system.

1. Landscape & maturity

.NET / DDD side

The modular monolith is now the pragmatic default recommendation for .NET enterprise teams: bounded-context-per-module boundaries and event-driven internal communication, without distributed-systems overhead — move to microservices only once scaling or organizational limits are actually hit medium [1][2]. Vertical Slice Architecture and DDD are increasingly framed as complementary rather than competing [3], though at least one dissenting voice argues the two need deliberate reconciliation, not just layering [4]. Both dominant .NET Clean Architecture reference templates — Jason Taylor's and Ardalis's — remain actively maintained into 2026, each recently adding lighter-weight/vertical-slice variants [16][17][18].

React / modular side

Feature-Sliced Design (FSD) is repeatedly asserted as the most widely adopted methodology for structuring large React codebases [5][6] medium confidence — consistent across sources but no named production case study at scale was found. "Module Federation vs. monorepo" is considered a false dichotomy by 2026 practitioners [7]. Next.js Multi-Zones and Module Federation solve different problems, not substitutes [8][9][10].

Tooling

.NET Aspire is cited as the primary orchestration tool for modular monoliths [11][12] low confidence — vendor/consultancy sources, one unverifiable adoption anecdote, and Aspire's own GitHub tracker shows production-hardening still open [13]. Monorepo split: Turborepo for JS/TS speed-without-ceremony, Nx for platform teams needing codegen and boundary enforcement [14]. The "63% of 50+-dev companies run monorepos" statistic is unverified [15].

2. Architecture patterns in practice

Backend

The hybrid consensus is explicit and multiply-sourced: Vertical Slice Architecture for CRUD-heavy APIs and fast delivery, Clean Architecture for complex shared domain logic — combined as "Pragmatic Clean Architecture" high [20][19]. Vertical Slice Architecture was popularized by Jimmy Bogard (creator of AutoMapper and MediatR) around 2018 [21]. Ardalis's own template now ships both a full Clean Architecture variant and a "Minimal" vertical-slice variant, with a migration path between them high [38][39].

A modular monolith gives most of DDD's structural benefit without microservices' operational cost [22][23]. The one first-person production account found (Jon P Smith): a 22-module bounded-context monolith was "brilliant," but DDD's rich-entity discipline cost more code and was compromised under real deadline pressure single-source anecdote [24]. Don't apply full Clean Architecture ceremony to simple CRUD apps [32][33]. Watch for "fake slices," "shared-kernel sprawl," and "behavior sprawl" from stacked pipeline behaviors [40][41].

Durable theory: a bounded context is the opposite of a microservice — it defines the largest valid model boundary, not a 1:1 sizing rule. Splitting by data entity instead of true bounded context produces a "distributed monolith." medium, durable ~7yrs [28][29]

Frontend

FSD creates natural frontend bounded contexts [25]. Micro-frontends solve team-coordination problems, not a default architecture — real difficulty appears post-launch: shared-state pain, CSS leaks, ballooning bundles [26][27]. Nx enforces boundaries via tags + ESLint; Turborepo's equivalent is newer and less mature [30][31]. Agree on a one-page integration contract before adopting micro-frontends at all [51].

Ecosystem shock relevant to pattern choice

MediatR, AutoMapper, and MassTransit all went commercial in 2025 under Lucky Penny Software high [34][35][36][37] — see §5.

3. Integration & interoperability

The Backend-for-Frontend (BFF) pattern is becoming standard for securing a React SPA against a .NET backend: tokens held server-side in an encrypted HttpOnly cookie, closing off XSS-based token theft high [42][43]. YARP is the common implementation vehicle [44].

NSwag remains the dominant OpenAPI toolchain for .NET; Kiota is Microsoft's newer alternative [45][46]. Real friction: NSwag v14 shipped breaking config changes, and generated clients had concrete bugs (route params, transient `JsonSerializerOptions` reallocation) high [49][50]. Contract drift is a real pain point; mitigate with CI-regenerated types from OpenAPI schemas [47][48][52].

The gap that matters most: no named production case study describes DDD bounded-context boundaries being explicitly mapped to (or kept independent from) React module boundaries. Only conceptual pieces exist — this is an open question the requester's project will answer without precedent.

4. Implementation reality

Teams new to Clean Architecture commonly find it unnecessary ceremony at first, then see the value after living with it — structure one feature this way first, not the whole codebase [55]. Even Jason Taylor's widely-used template has an open purity debate: its Application layer depends directly on EF Core high [56][57].

Sequencing matters: get bounded contexts (strategic) right before tactical DDD patterns, or results suffer [58]. Modular-monolith boundary enforcement relies on tooling (Contracts projects + NetArchTest/ArchUnitNET/NDepend in CI), not discipline alone [59][60].

Segment (140+ microservices → monolith) and Amazon Prime Video (serverless → monolith, 90% cost cut) corroborate the broader reversion trend — neither is a .NET/DDD/React case study, cited as landscape evidence only; Segment's account is from 2018 [61][62].

overturned The widely-recycled "Gartner: 60% regret microservices, 25% cost cut" statistic could not be traced to any real Gartner document — never cite it [63].

No source combines DDD tactics + Clean Architecture .NET + modular React into one team's 6–12 month retrospective — each is documented separately.

5. Ecosystem health

MediatR, AutoMapper, and MassTransit have all moved to commercial licensing under Jimmy Bogard's Lucky Penny Software, after his employer OSS sponsorship ended high [34][64][65][72]. This has fragmented the ecosystem within months: OSS mediator alternatives (Mediator, SwitchMediator, DispatchR, Concordia) are gaining traction [66][67]; ABP.IO publicly moved from AutoMapper to Mapperly [73]. FastEndpoints remains an actively maintained independent option [68].

Both Nx and Turborepo show healthy release cadences [69][70]. Durability differs: Turborepo ties to Vercel's business health; Nx's parent (Nrwl) hasn't announced new funding since a 2023-09 Series A — a mild five-year-regret flag [71][74][75]. Module Federation's core stays OSS; its maintainers built a commercial deployment layer (Zephyr Cloud) [76].

Cross-dimension insights

  • Pattern theory explains the implementation-reality trend. "Bounded context ≠ microservice" is the mechanism behind why Segment's and Prime Video's microservice-to-monolith reversions happened: splitting by data entity recreates coupling across a network.
  • Frontend and backend converge on the same idea, unvalidated as a pair. FSD (slice = feature) and modular-monolith-by-bounded-context are doctrinally the same idea — but no named team reports drawing that exact mapping in production. Treat it as this project's own hypothesis to validate early.
  • A licensing decision now sits inside an architecture decision. "Clean Architecture + CQRS + MediatR" — the safe, boring default — now implicitly requires a build-vs-buy-vs-alternative-OSS conversation that wasn't necessary in 2024.
  • Tooling is ahead on "how to integrate," silent on "how to structure the seam." BFF and OpenAPI-codegen guidance is prescriptive on mechanics; none of it touches whether bounded contexts should shape frontend module boundaries at all.

Contrary evidence

Red-team pass was not run (red_team = off, validation = normal). No adversarial pass was performed on the conclusions above — treat per-claim confidence flags as the operative caution, not an assumption these conclusions survived active disconfirmation-seeking.

Recommendations

  1. Backend: modular monolith, one module per bounded context, Contracts-only public surface, enforced in CI. high
  2. Inside each module, default to Vertical Slice Architecture; reserve full Clean Architecture for genuinely complex, long-lived domain logic. high
  3. Do not default to MediatR or AutoMapper without a licensing conversation — evaluate FastEndpoints, an OSS mediator, or Mapster/Mapperly. high on facts medium on which alternative
  4. Frontend: Feature-Sliced Design as the starting structural principle, enforced via Nx (or Turborepo for smaller teams). medium
  5. Don't reach for micro-frontends/Module Federation unless a genuine multi-team, independent-deploy problem already exists. medium-high
  6. Plan a BFF for auth and CI-regenerated OpenAPI→TypeScript clients rather than hand-maintained DTOs. high
  7. Sequence DDD adoption strategic-first — bounded contexts before tactical patterns; budget for real added cost. medium
  8. Never cite the "Gartner 60% microservices regret" statistic. overturned
