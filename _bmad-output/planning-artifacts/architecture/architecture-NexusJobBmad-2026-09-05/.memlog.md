- (decision) AD bounded-context split: three modules -- Identity (Company + JobSeeker accounts, credentials, sessions, display names), JobPostings (JobPosting entity + keyword search), Applications (Application entity, one-per-(seeker,posting) rule). Split by bounded context, not by data entity, to avoid the distributed-monolith failure mode. Prevents: two modules both modelling accounts or postings; ambiguous ownership of the apply-uniqueness rule.
- (decision) AD data ownership: Identity owns CompanyAccount + JobSeekerAccount; JobPostings owns JobPosting (holds ownerCompanyId by id only); Applications owns Application (holds jobPostingId + jobSeekerId by id only). A module writes ONLY its own schema; it reads another module's data only through that module's Contract, never by SQL against another schema. Prevents: divergent duplicate copies of an entity, cross-module writes, hidden coupling through shared tables.
- (decision) AD inter-module communication: synchronous in-process calls through published Contract interfaces registered in DI. No domain-event bus in v1. Each module ships a {Module}.Contracts project (interfaces + DTOs) that is the ONLY thing other modules may reference. Prevents: modules reaching into each other's internals; premature async/event infrastructure the v1 domain has no workflow for.
- (decision) AD persistence: one PostgreSQL database, schema-per-module (identity, job_postings, applications), one DbContext per module scoped to its schema. NO cross-schema foreign keys; cross-module references are by id only, integrity enforced in application code. Per-module EF migrations. Prevents: the database silently re-coupling modules that the code keeps separate.
- (decision) AD cross-module reads for the core loop: JobPostings->Identity resolves Company display name (FR-5). Applications->Identity resolves applicant name + email (FR-7). Applications->JobPostings resolves posting ownerCompanyId to enforce "a Company sees applicants only for its own postings" (FR-7) inside the Applications slice. All via Contract calls. Prevents: two modules enforcing the FR-7 ownership check differently, or neither.
- (decision) AD transaction boundary: every v1 user action mutates exactly one module's schema (sign-up = Identity, create posting = JobPostings, apply = Applications). No distributed transaction, no saga in v1. A future multi-module action would go through events (deferred). Prevents: a builder introducing a cross-module DB transaction or a two-phase write.
- (decision) AD composition root: a single ASP.NET Core host project references every module's implementation project and calls its AddXxxModule()/MapXxxModule() extension. The host is the ONLY project allowed to reference a module implementation; modules reference only each other's .Contracts. Prevents: an implicit dependency web where any module can construct any other.
- (decision) OQ-4 RESOLVED: email uniqueness is per-role. Two separate account tables (CompanyAccount, JobSeekerAccount), email unique within each, NOT globally. The same email may hold both a Company and a Job Seeker account as two distinct identities -- matches FR-1/FR-2 wording ("already registered as a Company" / "as a Job Seeker") and the EXPERIENCE.md role-toggle model. Offer to update the PRD so upstream does not diverge.
- (decision) AD auth topology: same-origin deployment -- the ASP.NET Core host serves the built React SPA as static files AND the API from one origin. No separate BFF proxy, no YARP, no Duende (avoids commercial licensing; minimal-ceremony for a single-deployable solo project). Alternative weighed: separate-origin SPA + BFF proxy -- rejected for v1 as unnecessary.
- (decision) AD auth mechanism: ASP.NET Core cookie authentication WITHOUT the ASP.NET Core Identity framework; reuse only Microsoft.AspNetCore.Identity PasswordHasher (PBKDF2-HMAC-SHA256) for hashing. HttpOnly + Secure + SameSite=Lax auth cookie carrying an account-type (role) claim. Antiforgery token required on state-changing requests. Passwords never logged (NFR). ASP.NET Core Data Protection keys persisted so cookies survive restarts. [ASSUMPTION] skipping the full Identity framework -- confirm.
- (decision) AD module internals: each module = one implementation project (NexusJob.Modules.{Context}) + one NexusJob.Modules.{Context}.Contracts project. Inside: Features/{Slice}/ folders each holding endpoint + handler + request/response + validation. No separate Domain/Application/Infrastructure projects for any v1 module (all three are CRUD-shaped; SM-C1). Endpoints = ASP.NET Core Minimal APIs invoking slice handlers directly via DI -- NO mediator library. Cross-cutting concerns (auth, validation, exception->ProblemDetails, logging) as middleware / endpoint filters. Alternative weighed: source-gen mediator -- deferred until pipeline-behavior pressure is real.
- (decision) AD API + data conventions: errors as RFC 9457 ProblemDetails (ASP.NET Core built-in); success responses return the resource representation directly, no custom envelope [ASSUMPTION]; primary keys = UUID v7 generated app-side, exposed as strings; timestamps UTC ISO-8601 stored as timestamptz; REST paths lowercase plural (/api/job-postings, /api/applications); integration/event names past-tense; Postgres identifiers snake_case; C# PascalCase.
- (decision) AD frontend structure: FSD layers app/pages/widgets/features/entities/shared with strict downward-only imports, enforced by an ESLint boundary rule in CI (mirrors the backend boundary discipline). Server state via TanStack Query; routing via React Router [ASSUMPTION]; no global client-state library in v1. API client = OpenAPI-generated TypeScript regenerated in CI from the host's OpenAPI document; hand-maintained DTOs banned. Tool NSwag vs Kiota decided at implementation [ASSUMPTION].
- (decision) AD frontend-mirrors-backend pilot: the "FSD slice == backend bounded context" mapping is adopted ONLY as a pilot on the Applications capability end-to-end, with an explicit checkpoint during implementation to confirm it pays off before propagating to the JobPostings / Identity slices. Revisit condition: after the first vertical slice ships. (addendum open item)
- (decision) AD search: FR-4 keyword search is a case-insensitive substring match implemented as a SQL query (ILIKE / EF Contains) inside JobPostings. No search engine, no separate search module or index in v1. Search + view-detail endpoints are AllowAnonymous (resolves PRD OQ-3 as assumed: only applying requires auth).
- (decision) AD operational envelope: single container image (host serving API + SPA build) + one PostgreSQL instance. Environments: Local (Docker Compose: app + Postgres) and ONE hosted environment for v1 [ASSUMPTION -- no staging/prod split required by SM-1]. Hosting platform undecided [ASSUMPTION -- candidates: single Docker host, Azure Container Apps, Fly.io, Render]. Config + secrets (DB connection string, Data Protection key) via environment variables. Per-module migrations applied on release. Structured JSON logging + a health endpoint; OpenTelemetry deferred. CI = GitHub Actions [ASSUMPTION]: build, arch tests, unit + integration (Testcontainers Postgres), one full-core-loop e2e test (SM-1), build image.
- (decision) AD CI architecture tests (ArchUnitNET, build-breaking): (1) no module implementation assembly depends on another module's non-Contracts assembly; (2) no .Contracts assembly depends on any implementation assembly; (3) only the host project depends on module implementation assemblies. Frontend: ESLint FSD layer-import rule, also build-breaking. These tests ARE the SM-2 deliverable.
