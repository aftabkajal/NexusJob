## Intent

**Problem:** 3.1b's `ApplyButton` renders nothing for a signed-out visitor — the exact case the epic's headline flow ("decide, sign up, apply — without leaving the posting") is built for. A signed-out visitor who wants to apply has no path from the posting detail page at all.

**Approach:** Give `ApplyButton` a third render state, `gate`, for a signed-out visitor: clicking it opens a new `apply-gate-modal` — the app's first modal, built from scratch (no dialog library in the project) — containing a Job-Seeker-fixed sign-up form. On successful `POST /api/auth/register`, the modal closes and the *same* `useApplyToPosting.apply()` from 3.1b fires automatically against the posting still on screen — reusing 3.1b's already-reviewed submit/confirm/retry machinery verbatim, so this story adds no second apply path. `Escape` / scrim-click cancel with no submission and no data lost from the posting view; focus is trapped in the modal while open and restored to the triggering button on close.

## Boundaries & Constraints

**Always:**
- FSD downward-imports-only: the new `Modal` is a domain-free `shared/ui` primitive (portal to `document.body`, `role="dialog" aria-modal="true" aria-labelledby`, Escape + scrim-click close, Tab/Shift+Tab focus trap, focus save-and-restore on open/close). The gate's form lives inside `features/apply-to-posting` (the same feature slice as 3.1b's button/hook — one slice owns the whole "apply" verb across both signed-in and signed-out entry points) and may import `entities/session` (for `authClient` + `sessionQueryKey`) and `shared/ui`/`shared/lib`, never a sibling `features/*`.
- The three field validators (`validateName`, `validateEmail`, `validatePassword`, `EMAIL_PATTERN`) move from `features/auth/model/useAuthForm.ts` to `shared/lib` (mirrors this codebase's own precedent: `shared/api/http.ts`'s CSRF plumbing and `toApiError` were both moved down when a second slice needed them) — `useAuthForm` is updated to import them from there; no validation-rule drift between the standalone auth surface and the gate.
- The gate's `useMutation` calls `authClient.register` / `authClient.login` directly (already shared via `entities/session`) — it does **not** import or extend `useAuthForm`/`AuthForm` (FSD forbids `features/apply-to-posting` importing `features/auth`, and `useAuthForm`'s `onSuccess` hardcodes `navigate('/')`, which must never fire here).
- Role is fixed to Job Seeker in the gate: `<RoleToggle value="jobSeeker" disabledValues={['company']} />` — the Company option renders, visibly disabled, per EXPERIENCE.md ("visually present but not the point of entry there"), reusing the `disabledValues` prop `RoleToggle` has carried unused since 1.4b for exactly this.
- On a successful register, the gate calls one `onAuthenticated` prop; the parent (`ApplyButton`) invalidates `sessionQueryKey` and calls its own existing `useApplyToPosting().apply()` — the identical function a signed-in Job Seeker's inline click already uses. A subsequent apply failure surfaces through 3.1b's existing `formError`/retry UI on the (now-visible, signed-in) button — no new failure UI this story.
- Focus trap and Escape/scrim-close are hand-rolled (no dialog/focus-trap library in `package.json`); native `Tab` order inside the panel plus a keydown-based wrap at the first/last focusable element is sufficient — mirrors the codebase's existing "no external library" posture (`RoleToggle`'s hand-rolled roving-tabindex is the nearest precedent).
- Modal visuals follow DESIGN.md's `apply-gate-modal` token block exactly: panel `--color-surface`, `--radius-xl`, `--space-6` padding, title in `--text-heading-*`; overlay and shadow are **raw, un-tokenized** values (`rgba(26 27 46 / 55%)` overlay, `0 20px 48px rgb(26 27 46 / 18%)` panel shadow) — matching `JobPostingCard.module.css`'s existing precedent that elevation/scrim values stay inline, not tokenized, while colour/radius/spacing stay `var(--token)` (tokens gate).
- Microcopy verbatim, do not reword: duplicate-email `This email is already registered as a Job Seeker.` (field error under email); apply-failure-after-auth-success reuses 3.1b's existing `We couldn't submit your application. Please try again.` — no new failure copy is introduced by this story.
- `npm run lint`, `npm run test:fsd-gate`, `npm run test:api-import-gate`, `npm run test:tokens-gate`, `npm test -- --run`, and `npm run build` are all green. No backend change, no OpenAPI regen (both endpoints this story calls already exist and are already in the generated client).

**Never:**
- No log-in path inside the gate this story (Decision, 2026-09-11): the gate is register-only, no `mode`/`switchMode` state, no 401 credential-mismatch form banner. A duplicate-email rejection shows only the inline field error; a returning visitor who already has a Job Seeker account uses the standalone "Sign up / Log in" surface to authenticate, then re-opens the posting and clicks Apply again.
- No new backend endpoint, no combined "register and apply" endpoint — two independent requests the SPA chains, exactly as 3.1a's Design Notes specify.
- No second apply implementation — the gate never calls `applicationsClient.apply` itself; only `useApplyToPosting.apply()` does, so 3.1a's idempotency and 3.1b's confirm/retry UI cover the gate's apply leg for free.
- No `z-index` token, no `--shadow-*` token category — this is the first overlay in the app; a raw `z-index` on the Modal's own overlay class and the raw shadow value above are enough for one consumer (mirrors "don't force a premature abstraction," `Page<T>`'s precedent on the backend).
- No change to `PostingDetailPage.tsx` — `ApplyButton` owns the gate entirely; the page passes only `jobPostingId` as it already does.
- The modal never persists typed field values across a close — reopening starts blank (the AC's "nothing is lost from the posting view" is about the posting content, not an in-progress form draft).

## Implementation Notes

- **Focus-trap escape found and fixed post-implementation.** `Modal`'s `getFocusableElements` selector (`button:not([disabled])`, etc.) matched `RoleToggle`'s disabled Company option — a plain enabled `<button>` taken out of native Tab flow via `tabIndex={-1}` rather than the `disabled` attribute. Verified empirically (a throwaway probe test against the real composed `ApplyGateModal`): `Tab` from the submit button wrapped to the disabled Company toggle instead of the active Job Seeker one, and `Shift+Tab` from the Job Seeker toggle — the true first reachable control — failed to match the wrap condition at all (it compared against the wrong "first") and fell through to native browser Tab handling, which is exactly the AC-violating "escapes the modal" case. Fixed by filtering `getFocusableElements`'s candidates on the live `.tabIndex` property (`!== -1`), which correctly excludes the Company button regardless of which selector clause matched it. Added a regression test to `Modal.test.tsx` covering a generic `tabIndex={-1}`-but-not-`disabled` control (mirroring `RoleToggle`'s exact pattern) so this class of bug is caught for any future `Modal` consumer, not just this one. The implementation subagent's own risk note had flagged the theoretical shape of this issue but assessed it as unreachable; it was reachable and is now closed.
- **Confirmation could go missing after a successful register+apply, found by the review's verification-gap layer and independently by blind-hunter.** `ApplyButton`'s `render === 'gate'` branch was a hard early return with no `applied`/`showConfirmation`/`formError` rendering; the only way out of it was `useSession()`'s own refetch (triggered by `invalidateQueries` in `onAuthenticated`) settling to a Job Seeker — a second, independent network request racing the `apply()` POST with no ordering guarantee. If `apply()` settled first, the UI stayed on the plain gate-trigger button with no visible confirmation despite the application having gone through. Fixed with a local `authenticatedViaGate` flag, set the moment the gate's register succeeds, which forces the normal button/confirmation/error branch regardless of what the (still in-flight) session refetch reports. Added a regression test that leaves the session mock at signed-out for the whole assertion and still expects the `Applied` button + confirmation to render.
- **A cancelled gate could still auto-apply, found by blind-hunter.** `useMutation` does not cancel its request or skip `onSuccess` on unmount; closing the gate (Escape/scrim) while `POST /api/auth/register` was in flight let a late-arriving success still call `onAuthenticated`, auto-submitting an application the visitor had explicitly cancelled — a direct AC violation ("Escape ... no application is submitted"). Fixed with a `cancelledRef` set on close and checked (then reset on reopen) before `onAuthenticated` acts; the account may still end up created server-side (the request was already sent and can't be recalled), but no application is submitted and the UI returns to the plain gate trigger, matching the AC's literal guarantee.
- **Escape stopped working once the submit button disabled, found while writing the regression test for the cancel fix above.** `Modal`'s Escape handling lived in a panel-scoped `onKeyDown`; a button that disables while it holds focus (the gate's submit button, once `isSubmitting`) drops focus to `document.body`, outside the panel's DOM subtree, so a keypress there never reached the panel's handler — the modal became uncloseable for the whole in-flight window, exactly when a visitor most plausibly wants to bail. Fixed by moving Escape handling to a `document`-level listener (mount/unmount only, mirroring the existing focus-restore effect's lifecycle), independent of where focus currently is; the Tab-trap stays panel-scoped, unaffected. Added a regression test that explicitly blurs to `document.body` before pressing Escape.
- **`authenticatedViaGate` didn't cover the `'hidden'` branch, found by edge-case-hunter.** The `if (render === 'hidden') return null` check ran on the raw `render`, computed *before* `effectiveRender`; if the `invalidateQueries`-triggered session refetch came back errored (or resolved to some other account) right after a successful register+apply, `render` itself could read `'hidden'` and the whole surface — confirmation included — would vanish. Fixed by computing `effectiveRender` first and checking `effectiveRender === 'hidden'` instead, so `authenticatedViaGate` overrides both the gate branch and the hidden branch alike. Added a regression test: session mock flips to an errored state right after a successful register+apply, and the `Applied` confirmation still renders.
- **`useApplyGateForm.handleSubmit` was missing the double-submit guard every sibling in this codebase has, found by edge-case-hunter.** `useCreatePostingForm.handleSubmit`, `useAuthForm.handleSubmit`, and `useApplyToPosting.apply()` all guard `if (mutation.isPending) return`; the gate's `handleSubmit` didn't, so a fast double-Enter could fire two concurrent `POST /api/auth/register` requests. Added the same guard and a regression test mirroring `useApplyToPosting`'s existing double-click-guard test.
- **Three small hardenings from the review, applied directly rather than deferred.** (1) `ApplyGateModal`'s `jobPostingId` prop — documented as "accepted for symmetry" and genuinely never used beyond a `data-job-posting-id` DOM attribute nothing reads — the attribute is dropped; the prop stays in `ApplyGateModalProps` since the parent still passes it. (2) `FieldErrors` was independently declared three times (`useAuthForm.ts`, `useApplyGateForm.ts`, `authValidation.ts`'s own `AuthFieldErrors`), which undercut this story's own stated reason for extracting the validators ("no drift"); `AuthFieldErrors` is now exported from `shared/lib` and both hooks alias `FieldErrors` to it. (3) `Modal` hardened for two edge cases unreachable via `ApplyGateModal` (which always supplies `initialFocusRef` and focusable fields) but real for a future consumer: a panel with no focusable content now falls back to focusing itself (`tabIndex={-1}` added to the panel), and the focus-restore effect guards a `previouslyFocused` element removed from the DOM before unmount (`.isConnected` check). Both covered by new `Modal.test.tsx` cases.

## Design Notes

- **Why the gate reuses `useApplyToPosting.apply()` instead of calling `applicationsClient.apply` itself.** A second, independent apply call site would double the places 3.1a's idempotency and 3.1b's confirm/retry UI need to be trusted correct. Routing the gate's success through the *same* function means this story adds zero new apply-submission logic — only a new way to reach the existing one.
- **Why `Modal` is `shared/ui`, not part of the feature.** It has no knowledge of auth, applications, or posting ids — a reusable dialog chrome primitive, the same rationale as `Container`/`Pagination`/`RoleToggle`. A future modal (none currently planned) would reuse it directly.
- **Why the validators move to `shared/lib` rather than being duplicated.** Unlike the backend's `Page<T>`/filter-duplication precedent (crossing a *module* boundary with no shared-kernel project), these are pure, dependency-free functions one layer-move away from a legitimate shared home — the exact situation `shared/api/http.ts` and `toApiError` were already extracted for. Duplicating validation rules risks silent drift from the server's `[StringLength]`/`[EmailAddress]` constraints in two places instead of one.
- **No z-index or shadow token added.** This is the first overlay the app has needed; `JobPostingCard.module.css` already establishes that elevation values stay raw, not tokenized. A second consumer would be the trigger to extract one, per this codebase's own stated design philosophy.
